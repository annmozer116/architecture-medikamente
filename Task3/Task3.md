# Задание 3. Оценка Data Encryption at Rest and In Transit

Вам необходимо разработать стратегию защиты данных в рамках всей системы. При этом важно учесть особенности шифрования данных, которые находятся в разных состояниях — при хранении и во время передачи.

В результате подготовьте классификацию данных, обоснование необходимости защиты выделенных классов и инструменты защиты данных.

1. Определим данные для защиты

| Категория                    | Данные                                             | Чувствительность | Риски                                     |
|------------------------------|----------------------------------------------------|------------------|-------------------------------------------|
| PII (прямые идентификаторы)  | ФИО, паспорт (серия, номер), СНИЛС, ИНН            | максимальная     | Идентификация личности, 152-ФЗ, репутация |
| PII (контактные)             | Телефон, email                                     | высокая          | Идентификация в комбинации, спам/фишинг   |
| PII (косвенные)              | Дата рождения,адрес, место работы/учёбы            | высокая          | Идентификация в комбинации                |
| PHI (медицинские)            | Диагнозы, история болезни, назначения, заключения  | максимальная     | Врачебная тайна (323-ФЗ), моральный ущерб |
| PHI (лабораторные/биометрия) | Результаты анализов, диагностики, снимки (МРТ, КТ) | максимальная     | Особые категории ПДн (152-ФЗ)             |
| Сканы документов             | Паспорт, полисы, согласия, договоры                | максимальная     | Концентрированная PII/PHI                 |
| FIN (платёжные)              | Счета, суммы, история оплат                        | высокая          | Мошенничество, коммерческая тайна         |
| USR (учётные записи)         | Логины, хеши паролей, сессии сотрудников           | максимальная     | Компрометация доступа ко всей системе     |
| Метаданные/системные         | ID пациента, даты записей, логи доступа, ID врачей | средняя          | Косвенная идентификация в комбинации      |

2. Базовые инструменты защиты

Защита в покое (хранение)
- TDE (Transparent Data Encryption) в PostgreSQL	
    - Шифрование таблиц/БД на уровне СУБД (AES-256)
- Шифрование на уровне приложения (application-level encryption) с ключами  
    - Шифрование отдельных полей (паспорт, особо чувствительные поля)
- KMS (Key Management Service), например HashiCorp Vault
    - Хранение и ротация ключей шифрования
- Шифрование файлового хранилища
    - Шифрование сканов и файлов (AES-256, server-side или client-side)
- Хеширование паролей (bcrypt/Argon2) + защита секретов	
    - Базовое требования хранения паролей не в открытом виде

Защита при передаче
- TLS 1.3 для всего веб-трафика и API
    - Шифрование канала браузер–сервер, сервер–сервер	
- mTLS или VPN для интеграций
    - Защита канала с лабораторией и 1С
- Защищённая почта или API для результатов лаборатории
    - * Исходя из предпложения что AS IS медсестра перекладывает результаты в систему*
    - Замена незащищённой почты на API с аутентификацией и TLS

Ограничение доступа
- Динамическое маскирование (DDM)
    - Подмена полей по ролям (ФИО → Иванов И. И., телефон → +7***7878)
- PII и PHI для ролей без права «полный доступ»
- Логирование и аудит запросов на доступ к данным
- RBAC/ABAC доступ к данным только по ролям и атрибутам
    -  например ресепшен не видит PHI, врач — видит данные только своих пациентов
- FIN: Токенизация платёжных реквизитов
    - Хранение токенов вместо реальных номеров карт 
- Принцип минимизации
    - каждая система и процесс должны оперировать необходимым и достаточным набором данных (например в аналитике вряд ли могут понадобиться номера паспортов -> они не должны быть представлены даже в обфусцированном виде)
- PII, PHI при передаче в BI/ML  при экспорте в аналитику
    - Псевдонимизация, удаление идентификаторов, агрегаты
        - медицинские данные должны быть обезличены
        - персональные данные при необходимости анализа должны быть обфусцированы (например агрегированы в возрастные группы, токенизированы ФИО и др.)

## 3. Автоматизированный контроль

Средства для непрерывного контроля за данными и выявления нарушений:

| Средство                                       | Назначение                                                                                                                                                                                    |
|------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Централизованное логирование и SIEM**        | Сбор логов доступа к БД, приложению, файлам; корреляция событий, расследование инцидентов. Фиксация: кто, когда, какой объект/запись запрашивал или изменял (CRUD по PII/PHI).                |
| **Аудит доступа к чувствительным данным**      | Логирование всех обращений к тегированным данным (PII, PHI, FIN) с привязкой к пользователю, роли и времени. Недопущение изменения и удаления логов без отдельного разрешения.                |
| **DLP (Data Loss Prevention)**                 | Контроль каналов (USB, почта, веб): блокировка или алерт при попытке передачи помеченных данных за пределы периметра. Сканирование исходящего трафика и вложений по ключевым словам и меткам. |
| **Проверка тегов в CI/CD (OPA, тесты)**        | В релизе проверять: тегированные поля не попадают в логи и отладочный вывод; не передаются в неразрешённые API; новые поля с PII/PHI помечены тегами перед выкаткой.                          |
| **Мониторинг аномалий доступа**                | Обнаружение массового чтения, необычного экспорта, доступа в нерабочее время или с нехарактерных IP. Алерты ответственным за безопасность и реагирование на инциденты.                        |
| **Контроль целостности файлов и конфигураций** | Выявление несанкционированных изменений критичных файлов (конфигурации, ключи, системные скрипты) — например, tripwire, проверка контрольных сумм, сравнение с эталоном.                      |
| **Регулярный пересмотр прав доступа**          | Периодическая сверка списка пользователей и их ролей с актуальным штатом; отзыв доступа при увольнении; проверка соответствия принципу минимальных привилегий.                                |

## 4. Реестр программных и аппаратных средств для защиты данных

| Тип | Средство | Назначение |
|-----|----------|------------|
| СУБД | PostgreSQL с TDE или шифрованием тома | Хранение PII, PHI, FIN с шифрованием в покое |
| KMS | HashiCorp Vault / облачный KMS (например, Yandex Cloud KMS) | Управление ключами шифрования и ротация |
| Сеть | Reverse proxy с TLS (nginx, Ingress, облачный LB) | Шифрование при передаче для веб и API (TLS 1.3) |
| Файлы | S3-совместимое хранилище с server-side encryption (SSE) | Сканы документов, выгрузки; шифрование в покое |
| Идентификация | Keycloak + Active Directory для сотрудников, LDAP для пациентов + MFA (TOTP или аппаратные ключи) | Учётные записи сотрудников (USR), защита от компрометации |
| Управление политиками | Самописный компонент/ OpenPolicyAgent | Конфигурация политик, единая точка управления доступом|
| Тэгирование данных | Таблица в PostgreSQL / Apache Ranger  | Реестр тэгов для данных, единая точка управления |
| ETL обфускация | Airflow dags применения политик  | Специализированные даги фильтрации и обфускации данных перед заливкой в аналитические БД |
| Подсистема обработки согласий | OneTrust  | Подсистема, управляющая согласием пользователя на хранение и обработку данных. Управляет удалением данных при отзыве согласия, проверяет наличие согласия перед использованием данных |
| DLP | DLP-решение (серверное или агентское) | Контроль каналов утечки на рабочих местах с доступом к PII/PHI |
| Антивирус | Антивирус на рабочих местах и серверах| Защита от вредоносного ПО и обнаружение атак |
| Аппаратно | VPN | Защита каналов с лабораторией/1С при необходимости соответствия отраслевым нормам |
