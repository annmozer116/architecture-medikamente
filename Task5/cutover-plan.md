# Задание 5. Cutover-план миграции информационной системы "Медикаменте"

Документ содержит анализ текущей ситуации, обоснование выбора стратегии миграции, поэтапный cutover-план, выявление рисков и распределение ролей между участниками процесса.

---

## 1. Анализ текущей ситуации и выбор стратегии миграции

### 1.1. Исходные данные

**Текущая система (As-Is):**
- Журналы приёма, учёт пациентов и платежей, медкарты, анализы — в Excel и сканах на общем диске.
- Учёт денежных средств — "1С:Бухгалтерия предприятия" (файловый режим); ТМЦ — "1С:Торговля и склад".
- Один физический сервер (Windows Server 2022): AD, DNS, DHCP, LDAP, файловый сервер, Exchange. ККМ интегрированы с 1С по OLE.
- Единого бэкенд-приложения нет; процессы в основном ручные, разрозненные данные.

**Целевая архитектура (To-Be):**
- Единая платформа: порталы (клиенты, ресепшен, врачи), платёжный шлюз, CRM, интеграция с лабораторией по API.
- Доменная архитектура с bounded contexts (Реестр пациентов, Расписание, Согласия, Медицинские данные, Биллинг, Классификация данных, Аудит, Аналитика).
- НФТ: конфиденциальность (152-ФЗ, 323-ФЗ), масштабируемость (филиалы, 5× рост данных), сопровождаемость, конфигурируемость.

**Бизнес-цели миграции:**
- Поддержать пятикратный рост объёма данных и открытие филиалов.
- Усилить безопасность медицинских карт и соответствие законодательству РФ.
- Перейти к единой системе хранения и управления данными с возможностью записи через портал и мобильное приложение.

### 1.2. Сравнение трёх вариантов миграции
Рассмотрим:
- High-level design: Применение широких архитектурных принципов: проектирование с учётом домена, определение модульных границ. Миграция планируется по этим границам.
- Parallel run: Запуск старой и новой системы параллельно с постепенным переводом нагрузки и сравнением результатов.
- Branch by abstraction: Постепенный перенос функциональности слой за слоем с использованием абстракций (интерфейсы/адаптеры), переключение реализаций без "большого взрыва".

| Критерий | High-level design | Parallel run | Branch by abstraction |
|----------|-------------------|--------------|------------------------|
| **Плюсы** | Чёткая целевая картина, согласованность с доменом (DDD), понятные границы модулей. | Снижение риска "большого взрыва", возможность сверки данных и отката на старую систему. | Инкрементальная поставка, возможность отката по фичам, меньшая нагрузка на единовременную миграцию данных. |
| **Ограничения** | Не задаёт сам механизм переключения; без доп. стратегии исполнения возможен "водопад" или разовый cutover. | Требует синхронизации данных между старой и новой системой. Текущая "старая система" — это Excel, файлы и 1С, а не одно приложение: постоянная двусторонняя синхронизация сложна и рискованна. | Требует дисциплины версий и согласованности контрактов абстракций; период двойного сопровождения (legacy-адаптер + новая реализация). |
| **Применимость** | Целевая архитектура и границы уже определены (Task2, DDD). Подход можно использовать как основу планирования этапов, но нужна конкретная стратегия переключения. | Сложно: нет единого "старого" приложения; синхронизация Excel/файлов <-> новая БД ненадёжна; двойной ввод и расхождения данных создают высокий риск. | Хорошо подходит: новая платформа строится "с нуля"; можно ввести абстракции (реестр пациентов, расписание, биллинг) с реализациями "legacy" (чтение/запись через адаптеры к Excel/1C) и "new" (PostgreSQL); переключение по контекстам. |

### 1.3. Обоснование выбора: Branch by abstraction

Выбрана стратегия **Branch by abstraction** в сочетании с уже выполненным **High-level design** (домен, модульные границы из Task2 и DDD).

**Почему:**
1. **Новая система строится с нуля** — единого монолитного кода для "Strangler Fig" нет, но есть чёткие bounded contexts (Реестр пациентов, Расписание, Согласия, Медицинские данные, Биллинг и т.д.). Для каждого контекста вводится абстракция (интерфейс/порт), за которой стоят две реализации: адаптер к legacy (Excel, 1С, файлы) и реализация на новой платформе (PostgreSQL и сервисы).
2. **Поэтапное переключение без "большого взрыва":** сначала один контекст (например, Расписание/запись на приём) переводится на новое хранилище за абстракцией, остальные продолжают работать через legacy-адаптеры; затем по очереди — Реестр пациентов, Биллинг, Медицинские данные.
3. **Снижение рисков синхронизации:** не требуется постоянная двусторонняя синхронизация двух работающих систем (как при Parallel run); миграция данных выполняется один раз при переключении контекста на новую реализацию.
4. **Сохранение 1С:** бухгалтерия и ТМЦ остаются в 1С; через ACL (Anti-Corruption Layer) биллинг новой платформы передаёт в 1С только нужные данные; внутренняя модель не зависит от 1С.
5. **Согласованность с уже выбранной архитектурой:** целевой дизайн (домен, границы) уже определён; Branch by abstraction задаёт конкретный механизм cutover по этим границам.

**Ограничения и митигация:**
- **Согласованность версий и контрактов:** абстракции должны быть стабильными; изменения контрактов — через явный процесс и версионирование. В плане заложены этапы проверки контрактов и регрессионного тестирования.
- **Двойное сопровждение:** на период переключения поддерживаются и legacy-адаптеры, и новые реализации. Срок жизни legacy-адаптеров ограничивается поэтапным отключением по контекстам; после полного cutover адаптеры удаляются.

## 2. Cutover-план (поэтапный план миграции)

1. Подготовка инфраструктуры и абстракций: 
    - Развёртывание целевой инфраструктуры (Kubernetes, PostgreSQL, объектное хранилище, IAM). Определение интерфейсов (портов) для контекстов: PatientRegistry, Schedule, Billing, MedicalData, Consent. Реализация legacy-адаптеров (чтение/запись из Excel, 1С, файлов).
    - Результат: инфраструктура доступна; все адаптеры проходят smoke-тесты.
    - Отв.: Технический директор, DevOps
2. Подготовка данных
    - Инвентаризация и очистка данных в Excel/файлах/1С. Определение категорий и тегов (PII_direct,PII_indirect, PII_contact , PHI, PHI_biometry, FIN и т.д.). Подготовка скриптов миграции по контекстам (пациенты → Реестр, записи → Расписание и т.д.). Проверка согласий и жизненного цикла данных.
    - Результат: реестр данных утверждён; скрипты миграции проверены на тестовой копии
    - Отв.: бизнес-аналитик, Технический директор, дата-аналитик
3. Тестирование
    - Интеграционные тесты абстракций (legacy vs new). Нагрузочное тестирование критичных сценариев. Проверка политик доступа (RBAC/ABAC) и тегирования. Регрессия после каждого переключения контекста.
    - Результат: Все критические сценарии проходят; SLA по задержкам и ошибкам в пределах нормы.
    - Отв.: QA, разработка
4.1. Cutover: Согласия и Реестр пациентов
    - Включение подсистемы согласий и реестра пациентов на новой реализации. Миграция данных пациентов в PostgreSQL. Переключение порталов на новую реализацию для операций с пациентами.
    - Результат: Регистрация и обновление пациентов идут только через новую систему; legacy-адаптер по реестру отключён.
    - Отв.: команда разработки
4.2. Cutover: Расписание (запись на приём)
    - Миграция данных расписания и записей. Переключение контекста "Расписание" на новую реализацию. Порталы ресепшена и клиентов работают с новой БД.
    - Результат: запись на приём и управление расписанием полностью в новой платформе
    - Отв.: команда разработки
4.3. Cutover: Биллинг и интеграция с 1С
    - Переключение биллинга на новую реализацию. Платёжный шлюз и передача данных в 1С через ACL. Кассиры и ресепшен работают через новые порталы.
    - Результат: оплаты и счета ведутся в новой системе; выгрузка в 1С стабильна.
    - Отв.: команда разработки, бухгалтерия 
4.4. Cutover: Медицинские данные и лаборатория
    - Миграция медкарт, осмотров, результатов анализов (в т.ч. из файлов/сканов в объектное хранилище). Включение API лаборатории. Переключение контекста "Медицинские данные".
    - Результат: Врачи и медперсонал работают с новой системой; лаборатория передаёт результаты по API. 
    - Отв.: команда разработки, медперсонал
4.5. Cutover: Аналитика и отключение legacy
    - Включение пайплайнов Airflow (фильтрация по согласию, анонимизация), заливка в озеро данных. Отключение всех legacy-адаптеров. Архивирование Excel/файлов только для аудита.
    - Результат: Нет обращений к legacy-адаптерам; отчёты BI строятся из нового хранилища.
    - Отв.: команда разработки, бизнес-аналитик, дата-аналитик
5. Мониторинг и стабилизация
    - Непрерывный мониторинг метрик (латентность, ошибки, доступ к тегированным данным), алерты SIEM, ежедневные стендапы по инцидентам. Сбор обратной связи от ресепшена, кассиров, врачей.
    - Результат: 2-4 недели без критичных инцидентов; метрики в пределах SLA.
    - Отв.: технический директор, DevOps 
6. План отката (на каждый этап 4.1-5)
    - Для каждого cutover определён критерий отката (например, >N% ошибок или недоступность критичного сценария). Откат = переключение абстракции обратно на legacy-адаптер и оповещение пользователей. Восстановление данных из бэка при порче данных. 
    - Результат: Документированные шаги отката и ответственные; репетиция отката на тестовой среде.
    - Отв.: Технический директор

### Критические моменты и минимизация рисков на этапах

| Критический момент | Риск | Меры минимизации |
|--------------------|------|-------------------|
| Миграция данных пациентов (этап 4.1) | Потеря или искажение ПДн/PHI | Инвентаризация и валидация до миграции; миграция в окно обслуживания с остановкой записи в legacy; сверка контрольных сумм и выборочная сверка записей после миграции; бэкап перед cutover. |
| Переключение расписания (этап 4.2) | Двойные записи или "потерянные" слоты | Транзакционная миграция; после переключения запрет записи в старые Excel/журналы; мониторинг конфликтов слотов в первые 48 часов. |
| Интеграция с 1С (этап 4.3) | Расхождение учёта денег с 1С | ACL с чётким контрактом; проверка платежей (новая система и 1С) ежедневно в течение двух недель; ручная сверка с бухгалтерией до стабилизации. |
| Доступ к медицинским данным (этап 4.4) | Недоступность медкарт для врачей | Поэтапное включение (сначала чтение из новой системы при записи ещё из legacy, затем полное переключение); горячая линия и быстрый откат по решению ответственного. |
| Согласованность версий абстракций | Разные сервисы ожидают разный контракт | Версионирование API и интерфейсов; регрессионные тесты при каждом изменении контракта; единый репозиторий контрактов |

## 3. Риски выбранной стратегии и план действий

### Ключевые риски для Branch by abstraction

| Риск | Описание | Вероятность / Влияние | План действий при реализации |
|------|----------|------------------------|------------------------------|
| **Согласованность версий** | Изменение контракта абстракции без обновления одной из реализаций (legacy/new) приводит к сбоям или неконсистентному поведению. | Среда / Высокое | Фиксация контрактов в репозитории (OpenAPI, IDL); проверка совместимости в CI; регрессия по сценариям "legacy" и "new" при каждом релизе. Ответственный: технический директор. |
| **Сложность и надёжность legacy-адаптеров** | Адаптеры к Excel/1С/файлам хрупкие (форматы файлов, версии 1С), возможны сбои при изменении формата или расположения данных. | Высокая / Высокое | Чёткая документация форматов и источников; минимальный набор операций через адаптер; мониторинг ошибок и таймаутов вызовов к legacy; план быстрого отката на предыдущую реализацию. Ответственный: разработчик бэкенда. |
| **Двойное сопровождение** | Одновременная поддержка двух реализаций увеличивает нагрузку и риск ошибок при изменениях. | Высокая / Среднее | Ограничение срока жизни legacy-адаптеров графиком cutover; изменения в доменной логике вносить только в новую реализацию; legacy — только чтение/запись без новой бизнес-логики. Ответственный: технический директор. |
| **Порядок переключения контекстов** | Неверный порядок (например, Биллинг раньше Реестра пациентов) приводит к зависимостям и сбоям. | Низкая / Высокое | Жёсткая последовательность по DDD-зависимостям: Согласия и Реестр > Расписание > Биллинг > Медицинские данные > Аналитика. Зафиксировано в cutover-плане. Ответственный: технический директор. |

### Общие риски миграции

| Риск | План действий | Ответственный |
|------|----------------|----------------|
| Недостаток компетенций (K8s, безопасность, IAM) | Обучение до этапа 0; при необходимости привлечение внешнего эксперта или найм. | Руководство, Технический директор |
| Несоответствие 152-ФЗ/323-ФЗ после переключения | Проверка тегов, политик и аудита до каждого cutover; тест-кейсы на доступ к тегированным данным в CI. | Технический директор, Ответственный за соответствие |
| Длительная деградация производительности | Нагрузочное тестирование до cutover; мониторинг латентности и алерты; кэширование политик и сокращение синхронных цепочек по рекомендациям Task4. | DevOps, Разработка |
| Сопротивление пользователей (ресепшен, кассиры, врачи) | Пилоты с ключевыми пользователями до массового переключения; обучение и инструкции; обратная связь после каждого этапа. | Бизнес-аналитик, Руководство |
