# Движок классификации данных перед загрузкой в аналитическое хранилище

Контекст:

- **Вход:** пакетные данные из операционных систем (PostgreSQL, выгрузки, файлы) со **структурами, подверженными изменениям** (новые поля, переименования, слияние источников) и **без предварительной разметки** по классу конфиденциальности
- **Ограничение:** в аналитическом хранилище **частично** хранятся конфиденциальные данные (агрегаты, псевдонимизированные наборы для отчётов), поэтому нужны отдельные зоны и меры защиты
- **Цель:** обеспечить аналитическую работу с данными в соответствии с Privacy by Design: минимизация, прозрачность, защита по умолчанию, классификация до попадания в хранилище.

---

## 2. Движок классификации данных перед пакетной загрузкой

Движок выполняет **классификацию и обогащение метаданных до записи в хранилище**: определяет класс конфиденциальности полей (PII и его подвиды, PHI, FIN, USR, метаданные), поддерживает эволюцию схемы и применяет политики (маскирование, фильтрация по согласию) перед загрузкой в зоны хранилища.

### 2.1. Основные компоненты (контейнеры)

| Компонент | Назначение | Учёт изменяющихся структур / неразмеченных данных |
|-----------|------------|---------------------------------------------------|
| **Приём пакетов (Batch Ingest)** | Приём файлов (Parquet, CSV, JSON), сообщений из очереди или стримов; буферизация и нормализация в единый внутренний формат. | Поддержка schema-on-read и опциональной схемы от источника; новые поля проходят дальше без жёсткой привязки к фиксированной схеме. |
| **Обнаружение и версионирование структуры (Schema Discovery)** | Выявление схемы (имена полей, типы, вложенности), присвоение версии схемы (schema_id), детекция изменений (новые/удалённые/переименованные поля). | При каждом новом наборе полей создаётся или обновляется версия схемы; классификатор и политики привязаны к полям, а не к фиксированному списку таблиц. |
| **Классификатор (Classification Engine)** | Присвоение классу конфиденциальности каждому полю: правила (по имени, типу, паттерну), опционально ML/паттерн-матчинг (регулярные выражения, словари). Для неразмеченных данных — классификация по умолчанию (например, «требует проверки») и последующее обучение по разметке. | Работает по актуальной схеме из Schema Discovery; новые поля классифицируются правилами и эвристиками; низкая уверенность -> тег «unclassified» и маршрутизация на ручную проверку или карантин. |
| **Реестр тегов и политик (Tagging & Policy Store)** | Хранение тегов (PII, PHI, FIN, USR) по полям и версиям схемы; политики маскирования/анонимизации и правила доступа по зонам. | Обновляется при появлении новых полей/схем; версионирование политик; поддержка наследования и переопределения по источнику/домену. |
| **Проверка согласий (Consent Check)** | Перед загрузкой в аналитику проверка согласия субъекта на обработку для цели «аналитика»; фильтрация записей без согласия. | Работает по идентификаторам в потоке (patient_id и т.п.); при отсутствии поля идентификатора — политика «не загружать» или «только агрегаты без идентификаторов». |
| **Трансформация и маскирование (Transform & Mask)** | Применение политик по тегам: удаление прямых идентификаторов, псевдонимизация (хеш), агрегация (дата рождения -> возрастная группа), маскирование. | Правила привязаны к тегам из реестра; для полей с тегом «unclassified» — консервативная политика (не передавать в открытом виде или не загружать до разметки). |
| **Загрузчик в хранилище (Warehouse Loader)** | Запись в соответствующую зону хранилища в зависимости от класса данных и политики: только обезличенные -> Gold, конфиденциальные с защитой -> Silver (зашифрованные партиции/таблицы). | Маршрутизация по результату классификации и трансформации; идемпотентность и повторная обработка при сбоях. |

### 2.2. Обработка изменяющихся структур и неразмеченных данных

- **Новые/изменённые поля:** Schema Discovery фиксирует новую версию схемы; Classification Engine присваивает тег по правилам и эвристикам; при отсутствии правила — тег `unclassified`, данные по этому полю не попадают в открытые зоны до проверки.
- **Карантин:** записи или поля с `unclassified` могут писаться в отдельную карантинную зону (доступ только ответственным за разметку); после разметки политики обновляются, данные перезагружаются.
- **Обратная связь:** результаты ручной разметки и исправления классификации используются для дообучения правил и (при наличии) ML-модели, что улучшает метрики со временем.

## 3. Организация хранилища данных (зоны и меры)

В хранилище частично хранятся конфиденциальные данные (например, псевдонимизированные наборы для разрешённой аналитики). Предлагается многослойная модель и дополнительные меры.

### 3.1. Зоны (слои) хранилища

По принципу трехслойности S3 DataLake House

| Зона | Содержимое | Доступ | Защита |
|------|------------|--------|--------|
| **Landing (временная)** | Сырые пакеты на время обработки. | Только движок загрузки. | Шифрование в покое (SSE), краткий срок жизни (удаление после успешной загрузки в Silver/Gold), без доступа для аналитиков. |
| **Silver (классифицированные)** | Данные после классификации и трансформации; партиции/таблицы по классу чувствительности (confidential, internal, public). | По ролям: конфиденциальные партиции — ограниченный круг (аудитор, безопасность); внутренние — аналитики с обучением. | Шифрование в покое по зоне (отдельные ключи для confidential); RBAC/ABAC на уровне таблиц и партиций; аудит доступа; срок хранения по политике. |
| **Gold (аналитическая)** | Только обезличенные/агрегированные данные для отчётов и ML. | BI, аналитики, дашборды. | Шифрование в покое, RBAC, аудит; запрет на хранение прямых идентификаторов и редких комбинаций (k-anonymity). |
| **Quarantine** | Поля/записи с тегом unclassified или с ошибками согласий. | Только ответственные за разметку и соответствие. | Изоляция, шифрование, минимальный срок хранения до разметки или удаления. |

### 3.2. Дополнительные меры

- **Шифрование в покое:** по зонам (Landing, Silver confidential, Gold) с использованием KMS; отдельные ключи для Silver confidential.
- **Контроль доступа:** RBAC по ролям (analyst, data_steward, auditor); ABAC при необходимости (цель запроса, тип данных). Запросы к Silver confidential логируются и могут требовать обоснования.
- **Аудит и мониторинг:** все обращения к Silver/Gold логируются; алерты на массовое чтение, экспорт, доступ к confidential; интеграция с SIEM.
- **Сроки хранения и удаление:** политики по зонам и по классу данных; автоматическое удаление/архивация по истечении срока; при отзыве согласия — удаление или обезличивание в Silver/Gold по процессу из подсистемы согласий.
- **Партиционирование по чувствительности:** в Silver таблицы/партиции разбиты по тегу (например, `sensitivity=confidential`), чтобы применять разные политики и ключи шифрования.

## 4. Метрики эффективности классификации и оптимизация

### 4.1. Метрики качества классификации

| Метрика | Описание | Использование |
|---------|----------|----------------|
| **Precision / Recall по классам** | По каждому тегу (PII, PHI, FIN): доля верно помеченных полей среди помеченных (precision) и среди всех реально чувствительных (recall). | Выявление переразметки (ложные срабатывания) и пропусков; приоритизация доработки правил и разметки для слабых классов. |
| **F1-score по тегам** | Баланс precision и recall по каждому классу конфиденциальности. | Сводная оценка качества; сравнение версий правил и моделей. |
| **Доля unclassified** | Процент полей/записей с тегом `unclassified` или низкой уверенностью. | Рост при появлении новых схем — сигнал к обновлению правил и разметке; целевое снижение со временем. |
| **Время до разметки (unclassified -> classified)** | Среднее время от появления нового поля до присвоения финального тега. | Оценка операционной нагрузки и риска задержки загрузки в открытые зоны. |
| **Согласованность с эталоном** | Сравнение с выборочной ручной разметкой (gold set) по подмножеству источников и схем. | Регулярная валидация; регрессии при изменении правил. |

### 4.2. Метрики процесса и системы

| Метрика | Описание | Использование |
|---------|----------|----------------|
| **Латентность пайплайна** | Время от поступления пакета до появления в целевой зоне (Silver/Gold). | Оптимизация производительности; SLA для пакетной загрузки. |
| **Throughput** | Объём данных (записей/байт), обработанных в единицу времени. | Планирование ресурсов и масштабирования при росте объёма. |
| **Доля записей, отфильтрованных по согласию** | Процент записей, не загруженных из-за отсутствия согласия. | Контроль соответствия PbD и политике согласий. |
| **Частота появления новых схем** | Количество новых/изменённых версий схем за период. | Планирование доработки классификатора и разметки. |

### 4.3. Как это помогает оптимизации

- **Классификатор:** низкий recall по PHI -> дообучение правил/модели и разметка примеров; высокий % unclassified -> расширение словарей и правил по именам полей/паттернам.
- **Пайплайн:** высокая латентность -> профилирование узких мест (Schema Discovery, Classification, Transform), масштабирование воркеров или партиционирование по источникам.
- **Риски:** рост доли unclassified или падение precision -> ужесточение политики для unclassified (не загружать в Gold до разметки), ревью и тесты перед выкаткой новых правил.

## 5. Масштабируемость и расширение системы

### 5.1. Рост объёма данных

- **Горизонтальное масштабирование:** приём пакетов и обработка — без состояния; можно увеличивать число воркеров (Airflow workers, Kafka consumers, отдельные поды движка). Партиционирование заданий по источнику, дате, схеме.
- **Партиционирование данных:** обработка по партициям (по дате, source_id, schema_version); параллельная загрузка в хранилище по партициям; партиционирование таблиц в Silver/Gold по дате и при необходимости по чувствительности.
- **Разделение чтения и записи:** реестр тегов и политик — отдельная БД/сервис с кэшем (например, Redis) для правил классификации; чтение схем — с реплик.
- **Асинхронность:** от приёма до загрузки — через очереди (Kafka, SQS); буферизация пакетов, батчинг для записи в хранилище.

### 5.2. Рост числа пользователей и источников

- **Мультитенантность источников:** идентификация источника (source_id, tenant_id) в метаданных пакета; отдельные политики и при необходимости отдельные схемы/теги по источнику; изоляция в хранилище по tenant при необходимости.
- **Управление схемами:** централизованный каталог схем с версионированием; при добавлении нового источника — регистрация схемы и начальная разметка полей; переиспользование правил по домену (например, «все поля с именем *birth* -> PHI/PII»).
- **Ограничение нагрузки:** rate limiting и квоты на приём по источнику; приоритизация критичных пайплайнов в очередях.

### 5.3. Расширение функциональности

- **Новые классы конфиденциальности:** добавление нового тега в реестр и правил в Classification Engine; обновление политик в Transform & Mask и правил доступа к зонам.
- **Новые форматы и источники:** адаптеры в Batch Ingest для новых форматов; единый внутренний формат; Schema Discovery и классификатор остаются общими.
- **ML-классификация:** опциональный блок в Classification Engine на основе обученной модели (например, по тексту значений или по метаданным полей); обучение на размеченных данных; A/B тесты с правилами для постепенного внедрения.

## 6. Связь с целевой архитектурой

- Движок реализует **аналитический слой с PbD**: классификация и минимизация данных до попадания в хранилище, зоны с разным уровнем защиты, проверка согласий.
- **Подсистема тегирования** (Apache Ranger / реестр в PostgreSQL) из Task2 используется как реестр тегов и политик; движок обогащает и использует теги при пакетной загрузке.
- **Подсистема проверки согласий** вызывается перед загрузкой в аналитику; фильтрация по согласию — часть движка.
- **Слой анонимизации/псевдонимизации** (Airflow в Task2) логически входит в компонент «Трансформация и маскирование» и «Загрузчик в хранилище»; движок классификации добавляет этап классификации **до** трансформации и маршрутизации по зонам.
- **Мониторинг и аудит:** события доступа к зонам и результаты классификации (в т.ч. unclassified) передаются в систему мониторинга и аудита.
